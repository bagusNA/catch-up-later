# Persistence and Storage

## SQLite

SQLite is the primary metadata database.

Recommended properties:

- WAL mode where supported.
- Foreign keys enabled.
- Busy timeout configured.
- Explicit migration system.
- Regular integrity checks in maintenance tooling.
- Parameterized queries only.

## Tables

Minimum tables:

- `users`
- `content_items`
- `artifact_versions`
- `artifact_assets`
- `tags`
- `content_item_tags`
- `reading_states`
- `capture_jobs`
- `capture_idempotency_keys`
- `search_documents` or FTS virtual tables
- `schema_metadata`

## Filesystem layout

Example:

```text
data/
  app.db
  artifacts/
    {ownerId}/
      {artifactId}/
        manifest.json
        content.html
        content.txt
        original.pdf
        assets/
          {assetKey}
  staging/
  backups/
```

The actual path layout may change, but:

- Paths MUST be generated by the backend.
- User input MUST never become a raw filesystem path.
- Artifact directories SHOULD be content-addressed or ID-based.
- Files SHOULD be written atomically using temporary files and rename.
- Deleting a content item SHOULD remove or garbage-collect its artifacts according to retention policy.

## Storage abstraction

Use an interface such as:

```kotlin
interface ArtifactStorage {
    fun stage(...)
    fun commit(...)
    fun open(...)
    fun delete(...)
    fun exists(...)
}
```

This allows future object storage without changing domain services.

## Backup

A consistent backup MUST include:

- SQLite database.
- Artifact directory.
- Configuration required to restore.
- Version information.

A database-only backup is invalid because artifacts are stored outside SQLite.

## Export

The future export format SHOULD be a portable archive containing:

- Manifest.
- Metadata.
- Reading state.
- Tags.
- Artifact files.
- Asset files.
